# 03 · 共通与专属分库：世界书架构与预算方法论

> 多卡同跑与群聊的地基：**共通库（全局挂载的独立 world 文件）+ 角色专属库（卡内嵌 character_book）**。本文给 schema、预算账方法与边界判定规则；实战版 77 条清单（含逐字引文回链）留在内部工作区。

## 〇、为什么要分库

ST 群聊里，**世界书只加载当前生成者的卡书**——嵌在角色卡里的共通设定对其他成员不可见。因此：

- 全局设定 → **共通库**（独立 world JSON，全局勾选激活），全员共享；
- 角色隐私（身份/秘密/私印象）→ **专属库**（卡内嵌书），天然隔离。

多卡发布时：各卡只内嵌自己的专属书，共通库单独一个文件带版本号（升版不覆盖旧文件，多卡引用同一版本）。

## 一、共通库条目六型 schema

| 型 | 含义 | keys 取词 | 内容谓词 | order 带位（参考） |
|---|---|---|---|---|
| SET | 世界规则/体系 | 概念词（魔力/等级/代价） | 存在谓词（「世界里有什么」） | 90-100，基石 constant=100 |
| LOC | 地点 | 地名+别名 | 存在谓词 | 94 |
| ORG | 组织 | 组织名+成员称谓 | 存在谓词 | 92 |
| OBJ | 物品/概念 | 物名+别称 | 存在谓词 | 90 |
| TL | 时间线锚 | 事件名+历法词 | 存在谓词（「何时发生了什么」） | 96 |
| FSH | 伏笔 | 对话表面词（见 §四） | 客观面+状态元数据 | plant 80 / payoff 88 |
| REL | 关系 | **只取对方名**（见 §五） | 行动谓词（「当X→双方倾向Y」） | 84 |

合成示例（一条 LOC）：

```
comment: 示例·灰港城
keys: 灰港城, 灰港, 北境港口
content: 【灰港城】北境最大自由港，四季起雾；公会总部所在。 [setting:rec-demo-0001(ch12)]
order: 94 / position: 0 / constant: false
```

每条带**回链**（`类型:record_id(chapter)`），指向上游正典记录——下游可对账，断言升级/作废后能跑回链体检。

## 二、预算账（方法论）

1. **token 估算法**：中文 ≈1.5 字符/token；keys/comment/extensions 不进 prompt（keys 在扫描侧判读，comment 不注入），只算 content。
2. **常驻成本**：constant 条目合计 = 每次调用的固定税（实战 4 条基石 ≈613 token/次）。基石只放「离开它们世界观就崩」的条目。
3. **最坏全触发**：全部条目进上下文的总 token（实战 ≈8k）。ST 默认 WI 预算 = context 的 25%，溢出按激活序裁剪：constant 先保，order 大者先保——**order 分层即裁剪优先序**。
4. **单条上限自检**：每条 content ≤450 字符（≈300 token），脚本可断言。

## 三、边界三问（逐条入库前自检）

- **Q1 离开该角色还成立吗？** 成立→共通库；不成立（私印象/私人记忆）→专属库（用 characterFilter 白名单本人）。
- **Q2 触发词是世界词汇还是角色行为词汇？** 共通库 keys 全部用世界词汇（地名/组织/物件/事件名/双方人名）；角色行为词汇（情绪词/关系事件动词）只出现在正文内、不做 key。
- **Q3 内容是「存在什么」还是「怎么做」？** 存在谓词→A 式直书；行动谓词（关系/习惯）→C 式 if-then（当X→倾向Y）。

**递归纪律**：每条自带直接 keys，无「另见」式裸交叉引用（实测递归不可依赖，见 [04](04-实验与判卷结论.md) 实验⑦）；伏笔双态用 NOT_ANY 副键与 order 分层替代递归。

**正典分界**：条目正文=断言忠实压缩+轻度连贯化；推测/声称/判读一律内嵌标记（「据推测」「据…转述」「声称态」）；冲突断言并列不仲裁；不做超出断言的脑补。三态引用规范：✅ confirmed→正典事实；◐ provisional→机器参考（标注）；⚠ quarantine→存疑待处理。

## 四、伏笔 plant/payoff 双态

伏笔条目成对：plant（谜面在位）+ payoff（兑现后），机制同[阶段化双态](02-阶段化双态世界书.md)：

| 对 | plant 态（order 80） | payoff 态（order 88 压住） | 机制 |
|---|---|---|---|
| 合成例 | 「灰塔的灯」之谜 keys=灰塔/塔灯/守塔人 | 灯塔真相揭晓 keys=塔灯熄灭/塔的真相 | plant 的 NOT_ANY 副键=payoff 词表：兑现事件词出现时 plant 退场，payoff（order 更高）压住 |

**防剧透规则**：plant keys 全部指向「会自然提起该钩子的对话表面」（物件/场景/人名），谜底词不作 plant 主键。

## 五、REL keys 纪律（防常驻化）

关系条目（A×B）的 keys **只取对方名，不含主角名**——否则 N 条关系条目会在任何主角相关对话同时全触发（N×~180 token 的常驻化风险）。非主角对取双方名+关系短语。REL 同键共存（一个名字触发多条关系）系设计：关系网成对入场，共通条目 order 低、专属视角条目 order 更高压制。

## 六、升级扩展位（留给 v2）

1. **关系递进**：REL 一页式客观面 → 拆 tier（初识→知情→誓约），配多级 keys；
2. **伏笔全量**：核心 N 条入库，长尾伏笔留 plant/payoff 机械化扩展；
3. **importance 排序**：extensions 留 `importance`（1-10）与 `last_used`（运行时回写）——超预算时按 Generative Agents 三分量（时间衰减+importance+relevance）截断插入，替代「命中即插」；
4. **时间线伪历推进**：day_offset/历法节庆词作 keys；
5. **版本治理**：书名带版本号（`xxx_common_v0.1`），升版不覆盖旧文件；
6. **源库升级对账**：extensions.sources 保留 record_id+chapter 全链路；上游记录 supersede/合并后跑一次回链体检。
